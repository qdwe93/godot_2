# DECISIONS — 기술 결정 기록

> 형식: 상황 → 선택지 → 결정 → 근거. 나중에 뒤집을 때 근거를 다시 따지기 위해 남긴다.

---

## D-001. 엔진 버전과 언어: Godot 4.7.1 + GDScript

**상황**: PC에 Godot 4.7.1 stable이 설치되어 있음. 언어는 GDScript와 C# 중 선택 가능.

**결정**: 설치된 4.7.1을 그대로 쓰고, **GDScript**를 쓴다.

**근거**:
- C#은 .NET SDK와 별도 빌드 단계가 필요해 CLI 자동화 파이프라인이 복잡해진다. 테스트 목적에 비해 과하다.
- GDScript는 Godot 엔진에 내장되어 있어 `--check-only`로 문법 검사, `--headless`로 실행 검증이 추가 설치 없이 된다. AI가 코드를 쓰고 즉시 검증하는 사이클에 유리하다.
- 주의: **4.7은 비교적 최신 버전이라 AI의 학습 데이터에 있는 예제가 구버전(3.x) 문법일 위험이 있다.** 3.x와 4.x는 API가 크게 다르다(`KinematicBody2D`→`CharacterBody2D`, `move_and_slide()` 시그니처 변경 등). 확신이 없는 API는 공식 문서를 확인한다.

## D-002. 렌더러: gl_compatibility

**상황**: Godot 4는 `forward_plus`, `mobile`, `gl_compatibility` 세 가지 렌더링 방식을 제공한다.

**결정**: `gl_compatibility`

**근거**: 2D 게임에는 forward_plus의 고급 기능(클러스터 라이팅 등)이 필요 없다. gl_compatibility는 OpenGL 3.3 기반이라 요구 사양이 낮고 실행이 가볍다. 헤드리스 CI성 검증에서도 문제를 덜 일으킨다. 나중에 고급 2D 라이팅이 필요해지면 그때 바꾼다(project.godot 한 줄 수정).

## D-003. codex 셸 실행 불가 → 역할 분리 (M0 시행착오)

**상황**: codex를 메인 코더로 쓰기로 했으나, 이 PC에서 codex의 샌드박스가 프로세스를 띄우지 못한다.
오류: `windows sandbox: runner failed during SpawnChild: CreateProcessAsUserW failed: 5 (액세스가 거부되었습니다.)`

**선택지**:
1. `--dangerously-bypass-approvals-and-sandbox`로 샌드박스를 끄고 codex에 셸 권한을 준다
2. codex는 파일 쓰기만 하고, 실행·검증·git은 Claude가 전담한다

**결정**: **2번.**

**근거**:
- 검증 결과 codex의 파일 쓰기(apply_patch)는 샌드박스에서도 정상 동작한다. 코드 작성이라는 본래 역할에는 지장이 없다.
- 애초에 정한 역할 분담(codex=코딩, Claude=검증·git)과 정확히 일치한다. 샌드박스를 끌 실익이 없다.
- 샌드박스 해제는 되돌리기 어려운 안전장치 제거다. 얻는 것 없이 위험만 늘린다.
- **파급 효과**: codex는 자기 코드를 스스로 실행해 볼 수 없다. 따라서 작업지시서에 **수용 기준을 구체적으로** 적어야 하고, Claude의 검증 단계가 필수다. 모든 작업지시서에 셸 금지 문구를 넣는다(CLAUDE.md 참고).

## D-004. 시각적 검증 방법: 인게임 스크린샷 저장 (M1에서 도입 예정)

**상황**: 헤드리스 모드는 렌더링을 하지 않아 화면을 볼 수 없다. 하지만 게임 개발은 "보이는 것"이 곧 결과물이라 시각 검증이 필수다.

**선택지**:
1. computer-use MCP로 데스크톱 스크린샷 촬영
2. 게임 코드 안에서 `get_viewport().get_texture().get_image().save_png()`로 직접 저장
3. 사용자에게 직접 실행해 보라고 요청

**결정**: **2번을 기본**으로 하고, 애매할 때 3번으로 보완한다.

**근거**:
- 2번은 완전히 스크립트로 제어되고(창 위치·포커스에 영향받지 않음), 정확히 게임 뷰포트만 캡처하며, 파일로 남아 비교가 가능하다. `--quit-after`와 조합하면 "N프레임 실행 → 캡처 → 자동 종료"가 한 줄로 된다.
- 1번은 사용자 승인이 필요하고 창 포커스·화면 상태에 영향을 받아 자동화 신뢰도가 떨어진다.
- 제약: **헤드리스에서는 안 된다.** 실제 창을 띄워야 렌더링 결과가 나온다. 따라서 캡처용 실행은 `--headless` 없이 돌린다.
- M1에서 구현하며, 커맨드라인 인자(`OS.get_cmdline_user_args()`)로 캡처 모드를 켜서 평소 플레이에는 영향이 없게 한다.

## D-005. 아트: 플레이스홀더 우선

**상황**: 무료 에셋(Kenney, itch.io 등) 사용이 허용됨. PC에 KayKit 등 에셋 팩도 있음.

**결정**: M8까지는 단색 도형 플레이스홀더로 간다. 에셋 교체는 M9.

**근거**:
- 보유 에셋은 대부분 **3D 모델**이라 이번 2D 프로젝트에 쓸 수 없다.
- 게임플레이 검증 단계에서 아트를 먼저 넣으면 스프라이트 크기·충돌 형태·앵커가 바뀔 때마다 재작업이 생긴다. 도형은 크기·색만 바꾸면 되므로 반복이 빠르다.
- 단, 색과 크기는 처음부터 구분되게 쓴다(플레이어/적/투사체/젬). 도형이라도 무엇이 무엇인지 화면에서 즉시 구분돼야 검증이 가능하다.

## D-006. 오브젝트 풀링: 아직 도입하지 않음 (재검토 시점 = M7)

**상황**: 서바이버류는 적과 투사체가 수백 개씩 생겼다 사라진다. `instantiate()`/`queue_free()` 반복은 GC 부하와 프레임 드랍의 주범이다.

**결정**: M2~M6은 단순 생성/삭제로 간다. **M7(웨이브·난이도)에서 실제 프레임을 측정한 뒤** 풀링 도입 여부를 결정한다.

**근거**:
- 성급한 최적화는 초기 구조를 복잡하게 만들어 기능 개발 속도를 떨어뜨린다. 적이 10마리일 때는 아무 차이가 없다.
- 다만 **나중에 풀링으로 갈아끼울 수 있게** 적·투사체의 생성/소멸을 각각 전용 함수(스포너/매니저)에 몰아둔다. 호출부가 흩어지면 나중 교체 비용이 커진다.
- 재검토 트리거: 적 200마리 상황에서 60fps 미달.

> **[M7b 결론 — 도입하지 않는다]** 실측했다. 적 **161마리(보스 포함)에서 최저 144fps**, 적이 8마리에서 160마리로 늘어나는 동안 프레임이 사실상 떨어지지 않았다. 목표 60fps의 2.4배다. 생성/소멸이 병목이 아니므로 풀링을 도입할 근거가 없다.
> 다만 생성 지점을 스포너 한 곳에 모아둔 구조는 유지한다 — 나중에 필요해지면 그 한 곳만 바꾸면 된다.
> 성급한 최적화를 피하고 측정 후 결정한다는 원래 판단이 옳았다.

## D-007. 월드 경계와 카메라: 고정 화면 유지 (M2에서 재검토)

**상황**: M1의 플레이어는 `get_viewport_rect()`(화면 크기)로 이동 범위를 제한한다. 화면 = 월드인 상태다. 그런데 M2에서 "화면 밖에서 적이 스폰된다"를 구현하려면 화면 밖 공간의 정의가 필요하다.

**선택지**:
1. 고정 화면 — 카메라가 움직이지 않고, 적은 화면 가장자리 바깥에서 들어온다
2. 카메라 추적 — 넓은 아레나를 두고 카메라가 플레이어를 따라간다

**결정**: **M2까지는 1번(고정 화면)을 유지**하고, 카메라 도입은 M7(웨이브) 시점에 재검토한다.

**근거**:
- 고정 화면이어도 "화면 밖에서 스폰"은 성립한다. 화면 사각형 바깥의 좌표에 적을 만들면 된다. M2의 목표(스폰과 추적)를 검증하는 데 카메라는 불필요하다.
- 카메라를 넣으면 `get_viewport_rect()`가 **화면 좌표**를 뜻하게 되어 월드 좌표와 어긋난다. 플레이어 경계 제한, 적 스폰 위치, 화면 밖 투사체 제거가 전부 좌표 변환 문제로 바뀐다. 한꺼번에 도입하면 문제가 겹쳐 원인 추적이 어렵다.
- **경계 계산을 한 곳에 모아두는 것**으로 전환 비용을 낮춘다. 나중에 카메라를 넣을 때 그 한 곳만 월드 경계 상수로 바꾸면 된다.
- 재검토 트리거: 적이 화면을 가득 채워 회피 공간이 부족해질 때(M7 예상).

## D-008. 테스트 방식: 씬 기반 자동 테스트 + PASS/FAIL/SKIP 계약

**상황**: 게임 로직을 검증할 방법이 필요했다. GUT 같은 외부 테스트 프레임워크 도입도 선택지였다.

**결정**: 외부 프레임워크 없이 **테스트용 씬을 만들어 헤드리스로 실행**하고, 약속된 토큰을 출력하게 한다.

```powershell
& "...\Godot_v4.7.1-stable_win64_console.exe" --headless --path "<프로젝트>" res://tests/test_player_movement.tscn
```

출력 계약: `TEST_CASE <이름> <PASS|FAIL|SKIP> <측정값>` + `TEST_RESULT <PASS|FAIL> passed=n failed=n skipped=n`, 실패 시 종료 코드 1.

**근거**:
- Godot CLI는 인자로 준 씬을 메인 씬 대신 실행한다. 추가 의존성 없이 테스트 러너가 생기는 셈이다. GUT는 애드온 설치·버전 호환 관리 비용이 있는데, 지금 규모에서 그만한 값을 못 한다.
- 종료 코드와 출력 토큰을 함께 쓰면 자동 판정이 확실해진다.
- **`SKIP`을 별도 상태로 둔 이유가 중요하다.** 헤드리스에서는 화면 크기를 신뢰할 수 없어 경계 검증이 불가능하다(devlog 002 참고). 이때 PASS로 처리하면 "검증했다는 착각"이 남는다. 못 한 검증은 못 했다고 표시하고, `skipped` 개수를 요약에 노출한다.
- **테스트의 기대값은 구현이 참조하는 값과 다른 출처에서 가져온다.** 구현이 런타임 뷰포트를 보면 테스트는 `ProjectSettings`(설계 의도)를 본다. 같은 출처를 쓰면 동어반복이라 절대 실패하지 않는 테스트가 된다.
- 재검토 트리거: 테스트 케이스가 30개를 넘어 러너 자체의 관리 비용이 커질 때 GUT 도입을 다시 검토한다.

## D-009. 조준 대상 탐색: 컨테이너 순회 → 그룹 조회로 변경 (M3)

**상황**: M2 문서에는 "`EnemyContainer`의 자식을 순회해 가장 가까운 적을 찾는다"고 계획했다. 그런데 무기는 `player.tscn` 안에 있고 컨테이너는 `main.tscn`에 있다 — **씬 경계를 넘는 참조**가 필요해졌다.

**선택지**:
1. 계획대로 컨테이너 참조 (NodePath 하드코딩 또는 외부에서 주입)
2. 그룹 조회 `get_tree().get_nodes_in_group("enemies")`

**결정**: **2번(그룹)**. `EnemyContainer`는 유지하되 조준용으로는 쓰지 않는다.

**근거**:
- NodePath(`../../EnemyContainer`)는 트리 구조에 종속된다. 플레이어 배치가 바뀌거나 테스트 씬처럼 구조가 다르면 즉시 깨진다. 외부 주입 방식은 안전하지만 배선을 빠뜨리면 조용히 아무것도 안 하게 된다.
- 그룹은 트리 구조와 무관한 이름표라 어디서든 조회된다. 테스트에서 씬을 직접 구성할 때 배선이 필요 없다.
- 비용: 호출마다 배열이 새로 생성된다. 발사는 초당 2회 수준이라 무시 가능. M6에서 무기가 늘어 호출이 잦아지면 재측정한다.
- `EnemyContainer`의 나머지 역할(개수 상한, 풀링 전환 지점)은 그대로 유효하다.

## D-010. 무기 사거리 도입 (M3)

**상황**: 사거리 제한이 없으면 무기가 스폰 직후(794px)의 적까지 조준해 **화면 밖에서 전부 사살**한다. 게임은 정상 동작하는데 플레이어 화면에는 아무것도 안 보인다(devlog 004).

**결정**: `attack_range = 350`을 도입하고, 사거리 밖은 조준 대상에서 제외한다.

**근거**:
- 350px는 화면 반높이(360)에 가깝다. 적이 화면에 들어온 뒤 교전이 시작되도록 하는 값이다.
- 사거리 판정은 **조준 정책**이므로 `find_nearest_enemy()` 안에 둔다. 발사 시점에 거르면 "대상은 찾았는데 못 쏜다"는 어정쩡한 상태가 생긴다.
- 경계값(거리 == 사거리)이 포함되는지 테스트로 고정했다. 부등호가 조용히 바뀌는 것을 막기 위해서다.
- 재검토: M10 밸런싱. 무기별로 사거리가 달라진다(GDD 6절).

## D-011. 스크린샷 캡처 기준: 렌더 프레임 → 게임 시간 (M3)

**상황**: 캡처 도구가 "N 렌더 프레임 대기 후 촬영" 방식이었다. 실측 결과 780프레임 대기가 **0.86초**, 20000프레임이 4.27초밖에 안 걸렸다. 13초를 기다린 줄 알고 찍은 사진에는 아직 스폰도 안 된 빈 화면이 담겼고, 멀쩡한 코드를 두 번이나 버그로 오판했다.

**결정**: `--capture-after=<초>`로 바꾸고 `--capture-frames`는 **제거**했다. 대기는 `get_tree().create_timer()`로 한다.

**근거**:
- SceneTree 타이머는 게임 시간 기준이라 프레임률과 무관하다. "12초 시점의 화면"이라는 의도가 그대로 코드가 된다.
- 오해를 부르는 옵션은 하위 호환으로 남기지 않는다. 호출부가 하나뿐이고 개발용 도구이므로 남길 이유가 없다.
- 성공 로그에 `elapsed`와 `frames_rendered`를 함께 출력한다. 실제로 이 두 값을 나란히 찍은 덕분에 "13초/779프레임 = 60fps"가 드러나 원인 범위를 좁힐 수 있었다. **도구는 결과뿐 아니라 무엇을 어떻게 측정했는지를 함께 보고해야 한다.**
- 주의: `create_timer()`는 기본적으로 `Engine.time_scale`의 영향을 받고 일시정지 중에도 진행된다. M5에서 레벨업 일시정지를 도입하면 캡처 타이밍에 영향이 있는지 확인해야 한다.

## D-012. 접촉 피해 판정: Area2D 폴링 (M4)

**상황**: 적에 닿았을 때 피해를 주는 판정이 필요하다.

**선택지**:
1. `move_and_slide()` 후 `get_slide_collision_count()`로 충돌 확인
2. `Area2D` 허트박스 + `body_entered` 시그널
3. `Area2D` 허트박스 + 매 물리 프레임 `get_overlapping_bodies()` 폴링

**결정**: **3번(폴링)**.

**근거**:
- 1번은 `CharacterBody2D`끼리 서로 밀어내며 미끄러져 접촉이 프레임마다 끊긴다. 판정이 불안정하다.
- 2번이 치명적으로 위험하다. `body_entered`는 **진입 순간에만** 발생한다. 적이 계속 겹쳐 있는 상태에서 무적이 풀리면 재진입 시그널이 없어 **적 무리 한가운데서 무한히 안전해진다.**

- 겹침 검사는 `if "contact_damage" in body:`로 한다. `get_property_list()` 순회는 물체마다 Dictionary 배열을 새로 할당하므로 매 프레임 돌릴 것이 못 된다.
- **측정된 특성**: Area2D 겹침 목록은 노드를 생성·순간이동한 직후 프레임에 갱신되지 않는다(실측 4프레임 지연). 테스트에서 배치 직후 판정하면 실패한다.

## D-013. 테스트 하네스 무결성 규칙 (M4)

**상황**: `player.gd`가 파싱 에러로 로드조차 안 되는 완전 파손 상태에서, 네 개 스위트 전부가 `TEST_RESULT PASS`와 종료 코드 0을 반환했다. 실행되지 않은 케이스는 집계에 안 잡히고(`passed=0 failed=0` → PASS), 이동 거리 비교 케이스는 0과 0을 비교해 통과했다.

**결정**: 모든 스위트에 아래 네 규칙을 강제한다.

1. `EXPECTED_CASE_COUNT`를 선언하고, 실행된 케이스 수가 다르면 `TEST_ERROR missing_cases`로 강제 FAIL
2. `passed=0`은 어떤 경우에도 PASS가 아니다
3. 케이스 실행 전 의존 대상 로드 여부를 점검하고, 실패 시 `TEST_ERROR setup_failed <무엇이>`로 즉시 중단
4. 거리·이동량·개수 비교 케이스는 측정값 또는 기준값이 0이면 FAIL (0 vs 0 통과 차단)

**근거**:
- 부서진 빌드를 초록불로 바꾸는 것은 테스트가 저지를 수 있는 최악의 실패다. 종료 코드만 보고 커밋했다면 스크립트조차 로드 안 되는 상태가 "완료"로 기록됐을 것이다.
- **검증 방법**: 고의로 파싱 에러를 주입해 `TEST_ERROR setup_failed` + 종료 코드 1이 나오는 것을 확인했다. 테스트를 고쳤으면 **실패해야 할 때 실패하는지**를 반드시 주입 실험으로 확인한다. 통과 확인만으로는 절반이다.
- 주의: 주입 실험 전에 **반드시 커밋**할 것. 커밋 없이 `git checkout --`으로 되돌리면 미커밋 작업이 사라진다(devlog 005에서 실제로 발생).

## D-014. codex 위임 방식: 수정 대상 파일은 전문을 첨부한다 (M5a) — **D-018로 번복됨**

**상황**: codex가 작업을 두 번 거부했다.

> "this session has no file-read tool besides shell access, and you explicitly prohibited shell commands"

M0에서 확인한 셸 실행 불가(D-003) 때문에 "셸 금지"를 표준 제약으로 넣었는데, **codex는 파일을 읽을 때도 셸을 쓴다.** 즉 이 PC의 codex는 기존 파일을 볼 수 없다. M1~M4가 굴러간 이유는 대부분 새 파일 생성이었고 지시서에 맥락을 충분히 적었기 때문이다.

**결정**: 작업 종류에 따라 위임 방식을 나눈다.

| 작업 | 방식 |
|---|---|
| 새 파일 생성 | 명세만 적어 위임 |
| **기존 파일 수정** | **파일 전문을 지시서에 붙여 넣어 위임** |
| 한두 줄 자명한 수정 | Claude가 직접 처리 |

**근거**:
- 전문 첨부는 토큰을 더 쓰지만, 거부당한 왕복(2회 × 약 1만 토큰)과 잘못된 추측으로 파일이 깨지는 비용이 훨씬 크다.
- 마지막 행이 필요한 이유: 이번 `call_deferred` 수정은 두 줄이었는데 거부로 왕복을 두 번 낭비했다. 수정 내용이 완전히 확정적이고 범위가 한두 줄이면 직접 처리가 합리적이다.
- 샌드박스 해제(`--dangerously-bypass-approvals-and-sandbox`)로 셸을 살리는 선택지는 여전히 택하지 않는다. 안전장치를 제거하는 대신 지시서를 두껍게 쓰는 쪽이 낫다.

## D-015. 물리 스텝 중 충돌 노드 조작 금지 (M5a)

**상황**: 적이 죽을 때 젬을 떨구자 다음 에러가 반복됐다.

```
Can't change this state while flushing queries. Use call_deferred() or set_deferred()...
   at: area_set_shape_disabled
```

호출 사슬: 물리 스텝 → 투사체 `body_entered` → `enemy.take_damage()` → `died` → 젬(Area2D) 트리 추가.

**결정**: 물리 스텝 중에 발생하는 시그널 안에서 충돌 도형을 가진 노드를 추가하거나 `monitoring`을 직접 바꾸지 않는다. `call_deferred()` / `set_deferred()`로 미룬다.

| 위치 | 조치 |
|---|---|
| `pickup_spawner.on_enemy_died` → 젬 추가 | `drop_gem.call_deferred(...)` |
| `player._die()` → `_hurtbox.monitoring = false` | `set_deferred("monitoring", false)` |
| `projectile` / `xp_gem` 자기 해제 | 그대로 — `queue_free()`는 프레임 끝으로 예약되므로 안전 |

**근거**: 물리 서버는 스텝 처리 중 충돌 객체 목록 변경을 허용하지 않는다. `queue_free()`가 안전한 이유도 같다 — 즉시 지우지 않고 프레임 끝에 지우도록 예약한다. 반면 `add_child()`와 속성 직접 대입은 즉시 반영된다.

## D-016. 씬 파일 편집 규칙 (M5a)

M5a에서 `.tscn` 관련 사고가 두 번 났다. 규칙으로 고정한다.

1. **섹션 순서**: `[gd_scene]` → 모든 `[ext_resource]` → 모든 `[sub_resource]` → 모든 `[node]`. 어기면 **씬 전체가 로드 실패**한다.
2. **`load_steps` = ext_resource 개수 + sub_resource 개수 + 1.** 리소스를 추가하면 같이 갱신한다.
3. **노드 블록 안에서 `script = ExtResource(...)`는 스크립트가 선언한 속성보다 먼저.** 속성은 파일 순서대로 적용되므로, `script`보다 앞선 스크립트 속성은 **에러 없이 조용히 버려진다.** 게임은 정상 실행되고 그 기능만 죽는다 — 가장 찾기 어려운 부류다.
4. 기존 파일에 추가할 때는 끝에 덧붙이지 말고 해당 섹션 안에 병합한다.

## D-019. 밝은 바닥의 대비는 외곽선으로 되찾는다 (M22)

서 있다.

사실상 같아진다. 지금 팔레트가 "전부 근검정보다 밝다"로 지어져 요소들이 위쪽에
몰려 있기 때문이다.

**선택지**:
1. 스프라이트에 **어두운 외곽선**을 둘러 실루엣으로 분리한다
2. 팔레트를 통째로 어둡게 다시 만든다 (밝은 바닥 위의 어두운 캐릭터)

**결정**: **1번.** 그리고 외곽선은 **그림을 다시 만들지 않고 코드로 두른다** —
알파를 팽창시켜 어두운 테두리를 만든다.

**근거**:
- 상용 게임이 밝은 바닥에서 실제로 쓰는 방법이다. 칠 색을 자유롭게 두고도
  실루엣이 분리되므로, 캐릭터를 어둡게 만들 필요가 없다
- 스프라이트가 이미 **알파 경계로 잘려 있어서**(ASSETS.md 9절) 팽창 처리가 그대로
  먹는다. **기존 8종을 그대로 살린다** — 2번은 그림 8장을 다시 만들어야 하는데
  codex 의 생성 품질 판정이 M11b·M15에서 양방향으로 틀렸던 전례가 있다

의미를 잃는다. 그리고 밝은 바닥에서는 **눈에 띄는 것이 밝은 것이 아니라 배경에서
먼 것**이므로, 순서 규칙도 "휘도 순서"가 아니라 **"대비 순서"** 여야 한다.

## D-020. 대비 "순서" 규칙을 버린다 — D-019의 딸려온 조건을 번복 (M22)

**상황**: [D-019](#d-019-밝은-바닥의-대비는-외곽선으로-되찾는다-m22)의 마지막 문단은

(주인공 > 보스 > 탱커 > 기본 > 빠른 > 젬 > 투사체)는 유지하라고 적었다.
M22 착수 시점에 계산해 보니 **그 둘은 동시에 성립하지 않는다.**

대비 순서가 휘도 순서와 같은 것은 **배경이 모든 요소보다 어두울 때뿐이다.**
바닥이 가장 어두운 요소(투사체, 휘도 0.150)를 넘어서는 순간 그 요소의 대비가
다시 올라가기 시작하고 순서가 접힌다.

| 바닥 | 배경 휘도 | 순서 위반 |
|---|---:|---|
| #3A3A4A | 0.044 | 0건 |
| #6A6480 (중간) | 0.137 | 0건 |
| #6E6989 ← 성립 상한 | 0.152 | 0건 |
| #726D8E | 0.165 | 1건 |
| **#A9A3C4 (레퍼런스급)** | 0.386 | **5건** |

레퍼런스급에서 실측 대비는 `보스 1.00 < 탱커 1.29 < 기본 1.51 < 빠른 1.58 <
젬 2.01 < 투사체 2.18` 로 **거의 뒤집힌다.**

**외곽선으로는 못 고친다.** 균일한 검은 테두리는 모든 요소를 같은 방향으로 밀기
때문에 순서를 만들지 못하고, 순위별로 두께를 다르게 줘서 순서를 만들려면
**가장 밝은 주인공을 가장 두껍게 검게 묻어야** 한다 — D-019가 지키려던 그림을
정확히 망가뜨리는 방향이다.

**선택지**:
1. 바닥을 #6A6480(중간)까지만 밝힌다. 계획이 그대로 성립하지만 레퍼런스와의 분위기
   차이를 절반만 줄인다
2. 레퍼런스급(#A9A3C4)까지 가고 **순서 규칙을 버린다**

**결정**: **2번** (사용자, 2026-08-15).

**근거**:
- 순서 규칙은 **M16 이전의 물건이다.** 카메라가 들어오기 전에는 주인공이 화면
  어디에나 있을 수 있었으므로 "주인공이 제일 눈에 띄어야 한다"를 휘도로 보장해야
  했다. 지금 주인공은 **항상 화면 한가운데 고정**이다 — 그 역할은 위치가 담당한다
- 규칙 2(3:1)는 살아 있고, 이제 **외곽선이 그것을 떠받친다.** 실측 5종 전부
  어두운 톤 5.9~6.3:1, 밝은 톤 7.3~7.9:1 이다
- 규칙 1이 진짜로 막던 사고("변종끼리 구분이 안 된다")는 순서가 아니라 **색차**로
  검사하는 편이 정확하다

**대체 규칙** (`tools/check_sprite_luminance.py` + `tests/test_visual_hierarchy.gd`):

| 검사 | 기준 |
|---|---|
| 실루엣 외곽 대비 | 타일의 **어두운 톤과 밝은 톤 양쪽**에서 3:1 이상 |
| 본체 색차 | 양쪽 톤에 대해 CIE76 dE 25 이상 |
| 변종 구분 | 적 4종 **서로** dE 20 이상 |
| 바닥 명도 대역 | 타일의 2/98 백분위 톤이 0.28~0.58 안 |
| 충전율 | 기존과 같음 (35% 이상) |

**한 톤만 통과하는 것은 통과가 아니다.** 어두운 톤 위에서 보이고 밝은 톤 위에서
사라지면 타일 무늬에 따라 요소가 깜빡이는 것과 같다.
