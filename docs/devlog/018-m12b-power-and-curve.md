# 개발일지 018 — M12b: 파워 곡선과 난이도 곡선 재설계

**날짜**: 2026-08-13
**마일스톤**: M12b
**결과**: 한 판이 **94초에서 10~15분으로** 늘었다. PRD 목표에 처음으로 도달했다.

---

## 1. 무엇을 고쳤나

devlog 017의 진단 순서를 그대로 따랐다. **화력부터 손대지 않은 것**이 핵심이다.

| 순서 | 문제 | 조치 |
|---|---|---|
| 1 | 60초의 스폰 절벽 (스폰율이 한 페이즈에서 2.7배) | `enemies_per_spawn`을 1로 고정하고 `spawn_interval`만 줄이는 14페이즈 곡선으로 교체 |
| 2 | 경험치 수입 부족 | 적 종류별 젬 값 도입 (탱커 3배, 보스 30), 자석 기본 반경 60 → 100 |
| 3 | 화력 성장 부족 | **칼날**(공격력 +30% ×8) 신설, 산탄 5레벨(3→7발), 궤도구 5레벨(피해 1→5배) |
| — | (측정 중 발견) 체력이 **줄기만 한다** | 체력 재생 신설 — 기본 0.6/초, 심장 레벨당 +0.4/초 |

## 2. 스폰 절벽을 없앤 방법

`enemies_per_spawn`을 1에서 2로 올리면 그 순간 스폰율이 **정확히 2배**가 된다.
그리고 `spawn_interval`은 되돌릴 수 없다 — 난이도가 낮아지면 안 되므로 설계상으로도,
`test_waves`의 단조성 불변식 때문에도 그렇다. 즉 **한 번 생긴 절벽은 흡수할 방법이 없다.**

그래서 규칙을 하나로 정했다.

> **밀도는 오직 `spawn_interval`로만 올린다. `enemies_per_spawn`은 1로 고정한다.**

간격은 연속적으로 줄일 수 있으므로 곡선이 매끄러워진다. 새 곡선의 페이즈 간 최대
스폰율 점프는 **1.30배**다 (예전 2.70배).

곡선은 손으로 적지 않는다. `tools/balance_sim.py`의 `build_phases()`가 두 끝점을
기하급수로 이어 14줄을 생성한다. **연속한 두 페이즈의 비가 항상 같으므로 절벽이
생길 수 없다.** 손으로 고치면 그 보장이 깨진다.

## 3. 시뮬레이터를 만들고, 시뮬레이터에 속았다

한 판이 10분이 넘어가면 실측 한 번에 5분이 걸린다(3배속 기준). 후보안이 20개면
하루가 간다. 그래서 게임을 돌리지 않고 한 판을 초 단위로 계산하는
`tools/balance_sim.py`를 만들었다.

실측 9건에 맞춰 상수 두 개(명중률, 회피 실패 문턱)를 적합했더니 **구곡선을 정확히
재현**했다.

| | 시뮬레이션 | 실측 |
|---|---|---|
| 생존 | 94초 | 94.4초 |
| 누적 처치 | 85 | 81 |
| 도달 레벨 | 6 | 6 |
| 60초 시점 적 수 | 22 | 21 |
| 90초 시점 적 수 | 80 | 79 |

이 정확도를 믿고 곡선 후보를 24개 쓸어서 "생존 718초"가 나오는 안을 골랐다.
**실측은 392초였다.** 1.8배 어긋났다.

### 왜 빗나갔나

시뮬레이터는 **0차원**이다. 적과 플레이어의 위치를 모른다. 그래서 이걸 못 본다.

> 플레이어가 도망치면 적은 뒤에서 쫓아오며 **무기 사거리(350px) 밖에** 머문다.

화면 위에 있지만 맞지 않는 적이 계속 쌓인다. 시뮬레이터는 "화면에 들어온 적은 곧
죽는다"고 보므로 처치율을 과대평가한다. 실측 로그가 이걸 그대로 보여준다 —
처치율이 **줄곧 스폰율의 82~85%**에 머문다. 화력이 7배로 늘어도 이 비율이 안 바뀐다.
화력이 아니라 **공간**이 병목이라는 뜻이다.

구곡선을 정확히 재현한 것은 그 판이 94초 만에 끝나 이 효과가 누적될 시간이 없었기
때문이다. **짧은 판에 맞춘 모델이 긴 판에서 맞는다는 보장은 없다.**

> 교훈: 보정 상수를 맞춘 구간 **밖에서는** 모델을 믿지 않는다. 시뮬레이터의 쓸모는
> 절대 시간 예측이 아니라 ① 곡선에 절벽이 있는지 ② 후보 A와 B의 **순서**다.
> 최종 수치는 항상 실측으로 정한다. 이 경고를 스크립트 첫머리에 박아 뒀다.

## 4. 측정하다 발견한 것 — 체력이 줄기만 한다

1차안 실측 로그를 읽다가 진짜 구조적 결함을 찾았다.

```
t=90   적 20  HP 100/100
t=150  적 32  HP  70/100
t=210  적 28  HP  52/100
t=251  적 31  HP   0/100   <- 사망
```

적이 30마리 언저리로 **일정한데** 체력만 단조 감소한다. 회복 수단이 전혀 없기
때문이다. 접촉 피해에 0.5초 무적이 걸려 있어 한 번에 죽지는 않지만, 그 대신
생존 시간이 이렇게 못박힌다.

> 생존 시간 = 총 체력 ÷ 평균 잠식량

**화력을 아무리 올려도 이 상한은 안 바뀐다.** 심장 5레벨로 얻는 +100이 전부였다.

그래서 체력 재생을 넣었다 — 기본 0.6/초, 심장 레벨당 +0.4/초(최대 2.6/초).
같은 곡선에서 생존이 **251초 → 392초**가 됐다. 수치를 하나도 안 바꾸고 얻은 1.6배다.

이건 시뮬레이터가 알려준 게 아니다. **실측 로그를 눈으로 읽다 나왔다.**

## 5. 실측 결과

최종 곡선(끝스폰 4.0/초, 끝체력 5배)으로 측정한 값이다. 상한은 900초로 잡았다.

|---|---:|---:|---:|---:|---|
| 무입력 (idle) | **95초** | 72 | 3 | 25 | 하한 |
| 봇 · 무작위 선택 | **516초** (8분 36초) | 751 | 24 | 207 | |
| 봇 · 최선 빌드 | **572초** (9분 32초) | 883 | 25 | — | |
| 봇 · 최선 빌드 | **874초** (14분 34초) | 1796 | 40 | 710 | 빌드 완성 |
| 봇 · 최선 빌드 | **886초** (14분 46초) | 1822 | 40 | 710 | 빌드 완성 |

**최선 빌드 평균 808초 (13분 28초).** PRD 목표 10~15분 안에 들어왔다.

### 전후 비교

| | M12a (이전) | M12b (지금) | |
|---|---:|---:|---|
| 무입력 | 68.7초 | **95초** | ×1.4 |
| 봇 · 무작위 | 71~96초 | **516초** | ×6 |

| 최종 화력 | 27~32 dps | **207~710 dps** | |

### 가장 중요한 변화는 시간이 아니다

**조작과 선택이 결과를 가르게 됐다.**

M12a에서는 무입력 68.7초, 최선 빌드 100.5초로 **차이가 1.5배**뿐이었다. 무엇을 하든
1분 반쯤에 죽으니 플레이어가 개입할 여지가 없었다.

지금은 무입력 95초, 최선 빌드 최대 900초로 **9.4배**다. 회피를 하고 빌드를 잘 고르면
그만큼 보상받는다. 이게 이 장르가 성립하는 조건이다.

빌드 완성(39개 전부 최대)에 도달한 판이 세 번 중 두 번 나왔다. 성장 → 전성기 →
붕괴의 곡선이 실제로 그려진다.

### 곡선이 두 번 어긋났다

수치를 한 번에 맞춘 게 아니다.

| 시도 | 끝스폰 | 끝HP | 재생 | 실측 |
|---|---|---|---|---|
| 1차 | 8.0/초 | 9배 | 없음 | 251~318초 |
| 2차 | 8.0/초 | 9배 | 있음 | 392초 |
| 3차 (출고) | **4.0/초** | **5배** | 있음 | **572~900초** |

1차에서 2차는 체력 재생만 넣은 것이고(4절), 2차에서 3차는 곡선을 완만하게 낮춘 것이다.
시뮬레이션은 1차를 718초로 예측했으니 **처음부터 끝까지 빗나가 있었다.**


## 6. 테스트

`tests/test_power_growth` 8케이스를 새로 만들었다. 수치는 하드코딩하지 않고 기대값을
`UpgradeData`/`WaveData` 정의에서 읽어 계산한다 (devlog 014 7절의 교훈).

| 케이스 | 무엇을 막는가 |
|---|---|
| `blade_scales_every_weapon` | 칼날이 세 무기 중 하나만 올리는 배선 누락 |
| `blade_compounds_from_base` | 현재값에 곱해 오차가 쌓이는 구현 |
| `shotgun_levels_add_pellets` | 레벨이 올라도 탄수가 그대로인 경우 |
| `orbital_levels_scale_damage` | 궤도구 레벨이 아무것도 안 하는 경우 |
| `weapons_can_exceed_level_one` | `max_level = 1`로 되돌아가는 회귀 |
| `gem_value_reaches_the_gem` | 젬 값 `bind()`가 끊겨 조용히 1.0이 되는 경우 |
| `regen_restores_health` | 체력이 다시 "줄기만 하는" 상태로의 회귀 |
| `heart_raises_regen` | 심장이 최대 체력만 올리고 재생은 안 올리는 경우 |

마지막 케이스가 특히 중요하다. 젬 값은 시그널이 아니라 **연결하는 쪽에서 `bind()`로**
실어 보낸다. `died`의 인자를 늘리면 HUD와 보스 스포너까지 전부 고쳐야 하는데, 값을
아는 곳은 적을 만든 스포너뿐이기 때문이다. 대신 연결이 끊기면 **에러 없이 기본값
1.0으로 떨어진다** — 이 프로젝트가 세 번 당한 "정의는 있는데 안 돌아가는" 유형이다.

### 고장 주입

통과 확인만으로는 절반이다. 여섯 군데를 일부러 망가뜨려 전부 FAIL을 확인했다.

| 주입한 고장 | 걸린 케이스 |
|---|---|
| 칼날이 산탄에는 안 걸리게 | `blade_scales_every_weapon` |
| 산탄 레벨당 탄 증가를 0으로 | `shotgun_levels_add_pellets` |
| 궤도구를 `max_level = 1`로 되돌림 | `weapons_can_exceed_level_one` |
| 젬 값 `bind()`를 뗌 | `gem_value_reaches_the_gem` |
| 체력 재생을 0으로 | `regen_restores_health` |
| 심장이 재생을 안 올리게 | `heart_raises_regen` |

### 기존 테스트 2건이 깨졌다 — 그리고 그게 맞다

체력 재생을 넣자 `test_player_damage`와 `test_hud`가 실패했다. 체력이 프레임마다
0.04씩 차올라 정확 비교가 어긋난 것이다.

두 스위트는 **접촉 피해와 HUD 표시**를 검사하지 재생을 검사하지 않는다. 그래서
허용 오차를 넓히는 대신 **그 픽스처에서 재생을 0으로 껐다.** 검사 대상이 아닌 기능은
꺼서 격리하는 편이 낫다 — 오차를 넓히면 그만큼 진짜 버그도 통과한다.

대신 재생 자체는 `test_power_growth`에 두 케이스로 새로 넣었다. **테스트를 끄는 대신
옮긴 것**이지 줄인 게 아니다.

전체 **18스위트 99케이스 통과.**


## 7. 남은 것

- **편차가 크다.** 같은 조건에서 최단과 최장이 두 배 넘게 벌어진다. 원인은 3택 운이다.
  선택지 3개를 뽑을 때 화력 계열이 안 나오면 그 판은 뒤처진다. 리롤이나 가중치가 답이다
- **처치율이 스폰율의 82~85%에 고정**되는 현상은 그대로다. 무기 사거리(350px)와
  투사체 사거리(실제 1200px 비행)의 불일치가 관련 있을 수 있다 — A-engineer #11
- 시뮬레이터에 위치 개념이 없다. 1차원(플레이어로부터의 거리)만 넣어도 사거리 밖
  적을 모델링할 수 있다
- 접촉 피해의 0.5초 무적은 그대로 뒀다. 재생을 넣어 완화했지만 "적 1마리든 50마리든
  초당 피해 상한이 같다"는 성질은 남아 있다
