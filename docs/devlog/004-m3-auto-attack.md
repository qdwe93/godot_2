## 2. 투사체를 `Area2D`로 만든 이유

플레이어와 적은 `CharacterBody2D`인데 투사체만 `Area2D`다.

| | CharacterBody2D | Area2D |
|---|---|---|
| 성격 | 물리적 실체. 밀고, 막히고, 미끄러진다 | 감지 영역. **겹쳤는지만** 알려준다 |
| 비용 | 충돌 해결 연산 필요 | 겹침 판정만 |

투사체에 필요한 건 "적과 겹쳤는가" 하나뿐이다. 물리적으로 적을 밀어낼 필요도, 벽에 막힐 필요도 없다. 게다가 서바이버류는 화면에 투사체가 수십 개씩 날아다니므로 가벼운 쪽이 유리하다. 관통 무기(하나의 투사체가 여러 적을 통과)도 Area2D가 훨씬 자연스럽다.

주의할 점 하나: Area2D의 충돌 시그널은 상대 종류에 따라 **다른 시그널**이 온다.

- 상대가 물리 바디(CharacterBody2D 등) → `body_entered`
- 상대가 다른 Area2D → `area_entered`

적이 `CharacterBody2D`이므로 `body_entered`를 연결해야 한다. `area_entered`를 연결했다면 아무 일도 일어나지 않는데, **에러도 경고도 없다.** 조용히 안 맞을 뿐이다.

## 3. 조준 대상을 찾는 방법 — 계획을 바꿨다

M2 문서에는 "`EnemyContainer`의 자식을 순회해 가장 가까운 적을 찾는다"고 적어뒀다. 실제로는 **그룹(`get_tree().get_nodes_in_group("enemies")`)을 쓰기로 바꿨다.**

이유는 **씬 경계를 넘는 참조** 문제다. 무기는 `player.tscn` 안에 있고, 적 컨테이너는 `main.tscn`에 있다. 서로 다른 씬이라 무기 입장에서 컨테이너로 가는 경로(`../../EnemyContainer`)를 하드코딩하면, 플레이어를 다른 위치에 배치하는 순간 경로가 깨진다. 테스트 씬처럼 구조가 다른 곳에서는 아예 성립하지 않는다.

그룹은 트리 구조와 무관한 **이름표**다. 어디에 있든 "enemies 딱지가 붙은 노드 전부"를 받아올 수 있다. 대가로 매 호출마다 배열이 새로 만들어지지만, 발사는 초당 두 번뿐이라 무시할 수 있는 비용이다.

`EnemyContainer`는 계속 유지한다. 조준용으로는 안 쓰지만 개수 상한 관리와 나중의 오브젝트 풀링 전환 지점으로서의 역할은 그대로다. **문서에 적어둔 계획이라도 구현하면서 더 나은 방법이 보이면 바꾸고, 바꾼 이유를 남긴다.**

투사체를 담을 컨테이너도 같은 이유로 그룹(`projectile_container`)으로 찾는다. 못 찾으면 `push_error` 후 현재 씬에 붙이는 폴백을 뒀다 — 시끄럽게 알리되 게임은 죽지 않게.

**투사체를 플레이어의 자식으로 붙이면 안 된다.** 자식 노드는 부모 좌표계를 따라가므로, 플레이어가 움직이면 이미 발사된 투사체가 같이 끌려간다.

## 4. 시행착오 ① — 테스트는 다 통과했는데 화면이 텅 비었다

### 증상

유닛 테스트 5개가 전부 PASS였다. 조준도 정확하고, 맞으면 죽고, 빗나가면 사라지고, 무한 증식도 없었다. 그런데 13초 시점 스크린샷을 찍었더니 **플레이어 혼자 있고 적도 투사체도 하나 없었다.**

### 원인 추적

임시 진단 스크립트를 만들어 1초마다 개수와 최근접 거리를 찍었다.

```
DIAG t=2s  enemies=1 projectiles=1 nearest=766.3
DIAG t=6s  enemies=2 projectiles=5 nearest=616.3
DIAG t=12s enemies=3 projectiles=5 nearest=526.3
```

적은 계속 생성되고 투사체도 날아다닌다. 그런데 **가장 가까운 적이 한 번도 520px 안으로 들어오지 못한다.** 화면 반너비가 640, 반높이가 360이니 대부분 화면 밖이다.

원인은 `find_nearest_enemy()`에 **사거리 제한이 없었던 것**이다. 스폰 지점(794px)에 적이 나타나는 즉시 사거리 무제한 무기가 조준해서, 적이 화면에 들어오기 전에 사살한다. 처치 속도와 스폰 속도가 균형을 이뤄 적 수는 2~3마리로 유지되는데, 그게 전부 화면 밖에서 벌어진다.

### 해결

무기에 `attack_range = 350`을 넣고, 사거리 밖의 적은 조준 대상에서 제외했다. 수정 후:

```
DIAG t=8s  enemies=5 projectiles=0 nearest=406.3
DIAG t=10s enemies=6 projectiles=2 nearest=286.3
```

적이 쌓이면서 접근하고, 350px 안에 들어온 9초쯤부터 사격이 시작된다.

### 교훈

이건 코딩 실수가 아니라 **설계 공백**이었다. 명세에 "가장 가까운 적을 조준한다"고만 적었지 "얼마나 멀리까지"를 안 적었다. 유닛 테스트는 명세에 적힌 것만 검사하므로 영원히 못 잡는 종류의 문제다.

> 유닛 테스트는 "각 부품이 명세대로 동작하는가"를 본다. "합쳐놓으면 게임이 되는가"는 못 본다. **눈으로 보는 검증이 따로 필요한 이유다.**

GDD 6절 무기 표에 사거리 열을 추가하고, 왜 필요한지 한 줄로 못박아 뒀다.

## 5. 시행착오 ② — 검증 도구가 잘못된 것을 재고 있었다

### 증상

사거리를 고쳤는데도 스크린샷은 여전히 텅 비어 있었다. 진단 스크립트(헤드리스)는 적이 286px까지 접근한다고 하는데 화면에는 없다. 헤드리스와 창 모드의 결과가 다른 셈이라 씬 구조(그리기 순서)를 의심했지만 정상이었다.

### 원인 추적

캡처 도구는 `--capture-frames=N`으로 **N번의 렌더 프레임을 기다린 뒤** 찍는 방식이었다. 60fps면 780프레임 ≈ 13초일 것이라 가정했다. 실제 시간을 측정해 봤다.

| 명령 | 실제 걸린 시간 |
|---|---|
| `--capture-frames=780` | **0.86초** |
| `--capture-frames=20000` | **4.27초** |

13초를 기다린 줄 알았는데 실제로는 0.86초였다. 첫 적이 1.5초에 스폰되므로 **적이 생기기도 전에 사진을 찍고 있었다.** 20000프레임으로 늘려도 3.8초라 여전히 부족했다.

즉 `await RenderingServer.frame_post_draw`를 루프로 도는 방식이 **한 번에 한 렌더 프레임씩 진행한다는 보장이 없었다.** 초당 수천 번씩 통과했다.

### 해결

기다리는 기준을 프레임에서 **게임 시간**으로 바꿨다.

```gdscript
await get_tree().create_timer(seconds).timeout   # 게임 시간 기준, 프레임률과 무관
await RenderingServer.frame_post_draw            # 그리기 완료를 한 번만 기다린 뒤 캡처
```

`--capture-frames`는 남겨두지 않고 **완전히 제거**했다. 오해를 부르는 옵션을 "구버전 호환"으로 남겨두면 언젠가 누군가 다시 쓴다.

그리고 성공 로그가 스스로를 설명하게 만들었다:

```
CAPTURE_SAVED <경로> elapsed=12.99s frames_rendered=779
```

이 한 줄이 결정적이었다. **13초 동안 779프레임 = 정확히 60fps**다. 즉 게임은 정상 속도로 돌고 있었고, 문제는 오로지 "프레임을 세는 루프"에 있었다. 앞으로 두 값이 어긋나면 로그만 봐도 바로 드러난다.

캡처 결과: 중앙의 플레이어, 접근하는 빨간 적 3마리, 아래쪽 적을 향해 날아가는 노란 투사체. 의도대로다.

### 남은 의문

프레임 대기 루프가 왜 그렇게 빨리 통과했는지 정확한 메커니즘은 확정하지 못했다. M2에서 같은 방식(600프레임)으로 찍은 스크린샷에는 적이 정상적으로 보였는데, M3에서는 780프레임이 0.86초로 끝났다. 창 포커스 상태에 따라 vsync 동작이 달라지는 것이 유력한 추측이지만 확증은 없다.

**원인을 완전히 규명하지는 못했지만, 시간 기준으로 바꿔서 이 변수 자체를 제거했다.** 그리고 매 캡처마다 elapsed와 frames_rendered를 함께 찍으므로 이상이 재발하면 즉시 보인다. 원인 불명인 채로 넘어가는 것과, 재발을 감지할 수 있게 만들어두고 넘어가는 것은 다르다.

### 교훈

> **검증 도구 자체가 틀릴 수 있다.** 도구가 조용히 엉뚱한 것을 측정하면, 멀쩡한 코드를 놓고 "버그가 있다"고 확신하게 된다. 실제로 이번에 두 번이나 그랬다.
>
> 그래서 도구의 출력은 **결과만이 아니라 "무엇을 어떻게 측정했는지"를 함께** 찍어야 한다.

## 6. 검증 결과

```
TEST_CASE no_enemies_no_shot        PASS projectile_is_null=true child_count=0
TEST_CASE nearest_target_chosen     PASS distance_a=300 distance_b=40 distance_c=180
TEST_CASE out_of_range_not_targeted PASS distance=900.000 attack_range=350.000 target_is_null=true
TEST_CASE in_range_boundary         PASS distance=350.000 attack_range=350.000 targeted=true
TEST_CASE hit_damages_and_kills     PASS frames_elapsed=11 enemy_valid=false projectile_valid=false
TEST_CASE miss_despawns             PASS lifetime=0.100 frames_advanced=9 projectile_valid=false
TEST_CASE no_unbounded_growth       PASS peak_count=3 final_count=3 bound=20
TEST_RESULT PASS passed=7 failed=0 skipped=0
```

`in_range_boundary`는 거리가 사거리와 **정확히 같을 때** 조준되는지 확인한다. 나중에 부등호가 `<=`에서 `<`로 바뀌는 식의 조용한 변경을 잡기 위한 케이스다.
