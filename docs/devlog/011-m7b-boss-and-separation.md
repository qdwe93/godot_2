## 2. 보스를 웨이브 표에 넣지 않은 이유

M7a의 웨이브는 종류별 가중치로 적을 뽑는다. 보스를 여기에 `weight: 1`로 넣으면 간단해 보이지만 **계속 나온다.** 확률적으로 뽑히는 것은 보스가 아니라 그냥 강한 잡몹이다.

그래서 `boss_spawner.gd`를 별도 노드로 만들었다. 경과 시간을 세다가 300초를 넘기면 한 번 스폰하고 `_has_spawned` 플래그를 세운다. **한 시간을 돌려도 두 번째는 없다.** 테스트 케이스 1이 스폰 후 한참 더 돌려 개수가 여전히 1인지 확인한다.

스폰 위치는 잡몹과 같은 화면 밖 원주 공식(반지름 794.3)을 쓴다. 보스라고 화면 안에서 갑자기 나타나면 회피할 시간이 없다.

M7a에서 배운 순서 함정도 그대로 적용했다. `enemy.gd`는 `_ready()`에서 `health = max_health`를 하는데 `_ready()`는 트리 진입 시 실행되므로, **HP·속도·크기 주입은 `add_child()` 이전에** 끝내야 한다. 테스트 케이스 2가 보스 체력이 설정값과 같은지 검사한다.

## 3. 적 분리 — 진짜 문제는 O(n²)

M2부터 미뤄온 부채다. 적들이 모두 플레이어를 향해 직진하니 결국 한 점에 겹쳐 한 덩어리가 된다.

해결 자체는 간단하다. 이웃 적들로부터 멀어지는 벡터를 추적 방향에 섞으면 된다. 문제는 **비용**이다.

```
적 160마리 × 각자 이웃 160마리 검사 = 25,600회 거리 계산 / 물리 프레임
```

물리 프레임은 초당 60회다. 초당 150만 회 거리 계산은 2D 게임에서 감당하기 어렵다.

세 가지로 줄였다.

| 기법 | 효과 |
|---|---|
| **4프레임마다 재계산**, 사이에는 직전 벡터 재사용 | 비용 1/4 |
| 재계산 프레임을 **인스턴스 ID로 분산** | 모든 적이 같은 프레임에 몰리지 않음 |
| 이웃 **12개까지만** 보고 중단 | 밀집 지역에서 조기 종료 |

분리 벡터는 매 프레임 바뀔 필요가 없다. 적은 초당 60px 정도로 움직이므로 4프레임(0.067초) 동안 위치는 4px밖에 안 변한다. **매 프레임 정확한 값보다, 충분히 최신인 값을 싸게 얻는 편이 낫다.**

추적이 우선이라는 것도 지켰다. 분리 가중치는 0.6이고 합친 뒤 정규화하므로, 사방이 막힌 적도 여전히 플레이어 쪽으로 다가온다 — 다만 덜 직선적으로. 테스트 케이스 5가 5마리 무리의 **평균 거리가 줄어드는지**(805 → 700) 확인한다. 분리가 추적을 이겨버리면 적들이 서로 밀어내기만 하고 플레이어에게 못 오는데, 그러면 게임이 성립하지 않는다.

케이스 6은 `separation_weight = 0`일 때 두 적이 겹친 채 유지되는지(거리 변화 0.0) 확인한다. **끄는 스위치가 실제로 꺼지는지**를 검사하는 것이고, 나중에 성능 문제가 생겼을 때 이 플래그로 원인을 분리할 수 있다.

## 4. 시행착오 — 테스트가 실패하지 않고 "멈췄다"

새 테스트를 돌렸더니 **10분이 지나도 끝나지 않았다.** 로그를 보니 이랬다.

```
SCRIPT ERROR: Parse Error: Expected statement, found "Indent" instead.
ERROR: Failed to load script "res://tests/test_boss_and_separation.gd" with error "Parse error".
```

들여쓰기가 깨진 두 줄 때문이었다(`if` 블록 안에 있어야 할 `prototype.free()`가 밖으로 나오고 `return null`만 안쪽에 남았다).

### 왜 실패가 아니라 대기였나

**테스트 스크립트가 로드되지 않으면 `get_tree().quit()`을 호출할 주체가 없다.** Godot은 스크립트 없는 빈 씬을 정상적으로 띄우고 무한 루프를 돈다.

M4에서 만든 하네스 보호 장치(`TEST_ERROR setup_failed`, 케이스 수 검증)는 **스크립트가 로드된 뒤에야 작동한다.** 파싱 단계에서 죽으면 그 코드에 도달조차 못 한다. 보호 장치의 사각지대였다.

### 해결

테스트 실행 명령에 엔진 차원의 안전장치를 붙였다.

```powershell
& "...Godot_..._console.exe" --headless --path "..." --quit-after 3600 "res://tests/<이름>.tscn"
```

`--quit-after 3600`은 60초 뒤 강제 종료다. 정상 테스트는 몇 초면 끝나므로 방해되지 않고, 파싱 실패 시에는 무한 대기 대신 빠르게 끝난다.

> **보호 장치는 자기가 실행될 수 있을 때만 보호한다.** 스크립트 안의 검증 코드는 스크립트가 로드되지 않는 상황을 막지 못한다. 그 바깥 계층(여기서는 엔진 CLI 플래그)에 하나 더 두어야 한다.

`CLAUDE.md`의 전체 스위트 실행 명령에 반영했다.

## 5. 성능 측정 — 풀링은 필요 없다

D-006에서 "적 200마리에서 60fps 미달이면 오브젝트 풀링 도입"을 재검토 트리거로 잡아뒀다. 이제 측정할 수 있게 됐으니 실측했다.

플레이어는 74초에 죽으므로 측정을 위해 **허트박스를 제거해 무적으로** 만들고, 레벨업 UI는 자동으로 첫 선택지를 고르게 한 뒤 320초를 돌렸다.

| 경과 | 적 수 | fps |
|---|---|---|
| 30초 | 8 | 145 |
| 90초 | 80 | 145 |
| 150초 | 110 | 145 |
| 210초 | 139 | 145 |
| 270초 | **160** | **145** |
| 300초 | 161 (보스 포함) | — |

```
DIAG DONE elapsed=320s peak_enemies=161 min_fps=144 boss_seen=true
BOSS_SPAWNED time=300.000000000056 health=500.0 scale=3.0
```

**최저 144fps.** 목표 60fps의 2.4배이고, 적 수가 20배로 늘어나는 동안 프레임이 사실상 떨어지지 않았다.

결론: **오브젝트 풀링은 도입하지 않는다.** 생성/소멸 비용이 병목이 아니다. D-006의 판단(성급한 최적화를 피하고 측정 후 결정)이 옳았던 셈이다. 대신 풀링으로 갈아끼울 수 있게 생성 지점을 스포너에 모아둔 구조는 그대로 유지한다 — 나중에 필요해지면 그때 한 곳만 바꾸면 된다.

분리 로직을 넣고도 프레임이 안 떨어진 것은 위의 세 가지 절감 기법 덕이다. 절감 없이 O(n²)로 짰다면 이 표는 달랐을 것이다.

## 6. 화면 확인

62초 시점 캡처에서 적들이 **한 덩어리가 아니라 흩어져** 있는 것을 확인했다. 다만 캡처 순간 레벨업 UI가 떠 있어 화면 일부가 가려졌다 — 무인 실행이 첫 레벨업에서 멈추기 때문이다(devlog 010). 캡처 도구와 일시정지가 겹치는 이 현상은 M8에서 화면 흐름을 정리할 때 함께 다룬다.
