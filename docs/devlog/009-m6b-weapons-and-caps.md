## 2. 왕관 연결 — 그룹으로 찾는 이유

경험치 배율은 M6a에서 계산만 되고 실제 경로에 안 걸려 있었다. 젬은 `player.add_experience(value)`를 부르므로 `player.gd`가 연결 지점이다.

그런데 플레이어가 `UpgradeManager`로 가는 경로를 하드코딩하면(`../UpgradeManager`) **테스트 씬에서 전부 깨진다.** 테스트는 저마다 다른 노드 배치를 만들기 때문이다. 그래서 그룹으로 찾는다.

```gdscript
var manager := get_tree().get_first_node_in_group("upgrade_manager")
```

세 가지를 함께 지켰다.

- **지연 조회**: `_ready()`가 아니라 필요할 때 찾는다. 실제 씬에서는 매니저가 플레이어보다 늦게 초기화될 수 있다.
- **매니저가 없으면 원래 값 그대로 전달**하고 **에러를 내지 않는다.** 기존 테스트 스위트 여럿이 매니저 없는 플레이어를 만든다. 여기서 `push_error`를 냈다면 멀쩡한 테스트들이 전부 시끄러워졌을 것이다.
- 그룹 등록은 **씬 파일에서** 했다(`groups=["upgrade_manager"]`). 매니저 스크립트를 수정하지 않아도 된다.

## 3. 상한 처리 — 선택지가 부족할 때가 진짜 문제

`max_level`은 M6a에서 이미 데이터에 있었지만 아무도 안 봤다. 이제 UI가 선택지를 뽑을 때 상한 도달 항목을 제외한다. 어려운 부분은 그 다음이다.

| 남은 항목 | 처리 |
|---|---|
| 3개 이상 | 평소대로 3개 |
| 1~2개 | **그만큼만 표시**하고 나머지 버튼은 숨김 |
| 0개 | **화면 자체를 띄우지 않고** 그냥 진행 (`LEVELUP_UI_SKIPPED` 로그) |

0개인데 화면을 띄우면 **고를 게 없어서 일시정지가 영원히 안 풀린다.** 게임 오버보다 나쁜 상태다. 테스트 케이스 5가 이걸 검사한다(`paused=false visible=false`).

## 4. 궤도구를 "플레이어의 자식"으로 만든 이유

궤도구는 투사체가 아니라 **플레이어의 자식 노드**다. 이러면 좌표 계산이 사라진다.

```gdscript
position = Vector2(cos(_angle), sin(_angle)) * orbit_radius
```

`position`은 부모 기준 상대 좌표라, 플레이어가 어디로 움직이든 궤도구는 자동으로 따라간다. 만약 월드 좌표로 만들었다면 매 프레임 `플레이어 위치 + 오프셋`을 계산해야 하고, 플레이어가 순간이동하거나 카메라가 붙는 순간 어긋난다.

**부모-자식 관계로 표현할 수 있는 것은 코드로 계산하지 않는다.** 씬 트리가 이미 해주는 일이다.

피해 판정은 두 가지를 지켰다.

- **폴링**: `body_entered`가 아니라 매 프레임 `get_overlapping_bodies()`. 궤도 안에 계속 머무는 적은 진입 시그널을 다시 안 쏜다 — 이 프로젝트에서 두 번 겪은 함정이다.
- **적별 쿨다운**: 전역 쿨다운이면 적 무리가 "다 같이 0.5초에 한 대"만 맞는다. 적 인스턴스 ID별로 마지막 피격 시각을 기록해 각자 0.5초마다 맞게 했다. 해제된 적의 항목은 정리해 딕셔너리가 무한히 자라지 않게 한다.

## 5. 시행착오 — 오진 한 번, 산술로 바로잡음

궤도구 피해 테스트가 실패했다.

```
FAIL health_before=100.00 health_after=78.00 frames=63 hits=6
```

63프레임(1.05초) 동안 피해 22. 쿨다운 0.5초면 3회(피해 12)여야 한다.

### 1차 진단 (틀림)

"앞선 케이스에서 쏜 산탄 탄환(피해 3)이 아직 날아다니다가 맞은 것"이라고 판단하고, 케이스 시작 전에 투사체를 전부 정리하게 했다. 결과:

```
FAIL health_after=78.00 hits=6 leftover_projectiles=0
```

**남은 투사체가 0인데 피해는 여전히 22.** 가설이 틀렸다.

### 2차 진단 (맞음) — 숫자를 방정식으로 풀었다

추측 대신 산술을 했다. 피해원은 셋뿐이다: 궤도구 4, 기본 총 5, 산탄 3.

> `4a + 5b = 22` → `a = 3, b = 2`

**궤도구는 정확히 3회 — 기대값 그대로였다.** 나머지 10은 플레이어의 **기본 총**이었다. 기본 총은 사거리 350 안의 적을 자동으로 쏘는데, 테스트가 만든 적은 플레이어 바로 위에 있으니 측정 63프레임 내내 총알을 맞고 있었다.

투사체를 미리 치우는 것으로는 소용이 없었다. **생산자가 계속 돌고 있었기 때문이다.**

### 해결과 교훈

측정 전에 기본 총과 산탄 노드를 아예 제거했다. 결과 `health_after=88.00 hits=3` — 정확히 12 피해.

> **한 시스템의 출력을 측정할 때는 같은 숫자에 쓰는 다른 시스템을 꺼야 한다.** 쌓인 상태를 치우는 것만으로는 부족하다.
>
> 그리고 **측정값이 기대 단위의 배수가 아니면 다른 출처가 섞인 것이다.** 22가 4로 나누어떨어지지 않는다는 사실 하나가 "오염이 있다"를 확정해 줬고, 방정식이 오염원을 정확히 지목했다. 로그에 원시 숫자를 남겨두지 않았다면 "대충 너무 많이 맞네"에서 멈췄을 것이다.

이번에도 궤도구 코드는 처음부터 옳았다. **세 번 연속으로 실패 원인이 구현이 아니라 측정 쪽에 있었다**(M3 캡처 도구, M5a 람다 캡처, 이번 테스트 격리).
