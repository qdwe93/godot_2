## 2. 핵심 함정 — 일시정지하면 UI도 멈춘다

이 마일스톤의 거의 전부가 이 한 줄이다.

```gdscript
get_tree().paused = true
```

Godot에서 트리를 일시정지하면 **모든 노드의 처리가 멈춘다. UI도 예외가 아니다.** 그래서 순진하게 구현하면 이렇게 된다.

1. 레벨업 → 일시정지 → 선택 UI 표시
2. 플레이어가 버튼을 클릭
3. **아무 일도 안 일어난다.** 버튼도 멈춰 있으니까
4. 영원히 멈춘 화면. **에러 메시지는 단 한 줄도 없다**

해결은 UI 루트의 `process_mode`를 바꾸는 것이다.

| 값 | 이름 | 동작 |
|---|---|---|
| 0 | `INHERIT` | 부모를 따름 (기본값) — 일시정지 시 멈춤 |
| 1 | `PAUSABLE` | 일시정지 시 멈춤 |
| 2 | `ALWAYS` | 일시정지와 무관하게 항상 동작 |
| **3** | **`WHEN_PAUSED`** | **일시정지 중에만 동작** |

레벨업 UI에는 `3`(`WHEN_PAUSED`)이 정확하다. 평소에는 꺼져 있고 멈췄을 때만 산다. `2`(`ALWAYS`)도 동작은 하지만, 게임이 도는 동안에도 UI가 계속 처리되어 불필요하다.

자식 노드는 기본값 `INHERIT`이므로 **루트에만 지정하면 전체가 따라온다.**

```
[node name="LevelUpUI" type="CanvasLayer"]
process_mode = 3
```

`CanvasLayer`를 루트로 쓴 이유는 별개다. CanvasLayer 아래 노드는 카메라 이동·줌의 영향을 받지 않아 화면에 고정된다. 메뉴 오버레이의 표준 선택이다.

## 3. 연속 레벨업 — 대기열이 필요한 이유

경험치 곡선상 젬 하나로 여러 레벨이 한 번에 오를 수 있다. `level_system.add_experience(30)`을 부르면 `leveled_up` 시그널이 **같은 프레임에 세 번** 발생한다.

대기열 없이 구현하면 세 번째 시그널이 앞의 두 화면을 덮어써서, 플레이어는 선택을 세 번 해야 하는데 한 번만 하게 된다. 그래서 시그널을 받으면 즉시 표시하지 않고 **쌓아두고, 선택이 끝날 때마다 다음 것을 꺼낸다.**

```
leveled_up ×3 → 대기열 3 → 화면 표시(대기 2) → 선택 → 화면 표시(대기 1)
              → 선택 → 화면 표시(대기 0) → 선택 → paused = false
```

**일시정지 해제는 대기열이 빈 뒤에만** 한다. 테스트 케이스 5가 이걸 검사한다(`screens=3 queue_after= 1/0/0`).

## 4. 테스트 설계에서 신경 쓴 두 가지

### ① 일시정지가 테스트 자신도 멈춘다

테스트 씬도 트리의 일부라 `paused = true`가 걸리면 같이 멈춘다. `await get_tree().physics_frame`으로 기다리면 **영원히 안 돌아온다.** 테스트 루트의 `process_mode`를 `ALWAYS`(2)로 두고, 일시정지 이후에는 `process_frame`을 쓰도록 구성했다.

### ② 테스트 경로와 실제 경로를 같게 만들었다

버튼 클릭을 코드로 흉내 내는 대신, 공개 메서드 `choose(index)`를 두고 **버튼의 `pressed` 핸들러도 같은 `choose()`를 부르게** 했다. 테스트가 검증하는 코드와 실제로 실행되는 코드가 동일해진다.

다만 한계는 분명히 해둔다. `choose()`를 직접 호출하는 것은 **입력 처리 경로를 거치지 않는다.** `process_mode`가 잘못돼도 이 호출은 성공한다. 그래서 케이스 3은 동작 확인에 더해 **`process_mode` 값 자체를 3인지 검사**한다. 설정 실수는 이걸로 잡히고, 실제 클릭 가능 여부는 아래 눈 검증으로 확인했다.

## 5. 실제 게임에서의 확인 — 강제 레벨업 진단

지금 밸런스로는 가만히 두면 레벨업이 일어나지 않는다. 젬은 적이 죽는 약 350px 지점에 떨어지는데 자석 반경은 60px이라, 움직이지 않는 플레이어는 영원히 줍지 못한다(M5a에서 확인).

그래서 임시 진단 씬을 만들어 실제 `main.tscn`을 띄우고 1.5초 뒤 경험치를 강제 지급한 다음, 뷰포트를 PNG로 저장했다.

```
LEVELUP_UI_SHOWN level=2 choices=gloves,heart,crown
LEVEL_UP level=2
DIAG granted_experience paused=true
DIAG capture error=0 paused=true
```

캡처 결과: 어두워진 배경 위에 "레벨 업!" 제목과 한글 선택지 세 개(장갑 - 공격 쿨다운 -8% / 심장 - 최대 HP +20 / 왕관 - 경험치 획득 +10%). 게임은 정지 상태.

**주의**: 이 진단은 `main.tscn`의 `CaptureHelper`를 제거하고 직접 캡처했다. 캡처 헬퍼는 촬영 후 스스로 게임을 종료하는데, 레벨업이 일어나기 전에 끝나버리기 때문이다. 검증 도구끼리 충돌한 사례다.

## 6. 시행착오가 없었던 이유

M5a에서 6건이 터졌는데 M5b는 0건이었다. 차이는 **작업지시서에 지금까지의 규칙을 전부 명시**한 것이다.

- Variant 추론 금지
- 기존 파일에 덧붙이지 말고 병합
- `.tscn` 섹션 순서, `load_steps` 계산법, `script` 선언 위치
- 수정 대상 파일은 **전문을 지시서에 첨부** (D-014)
- 테스트 하네스 무결성 4규칙

특히 마지막 두 개가 컸다. `main.tscn`을 수정해야 했는데 전문을 붙여 보내자 한 번에 정확히 처리됐다. 이전 두 번은 파일을 못 읽어 거부당했던 작업이다.

> 시행착오는 기록해두면 다음 작업지시서의 체크리스트가 된다. **문서화가 실제로 다음 마일스톤의 비용을 낮췄다.**

한 가지 미완: codex가 `CLAUDE.md` 수정만 거부했다(전문을 안 붙여준 파일이라). 그 부분은 직접 작성하면서, 겸사겸사 여섯 스위트를 한 번에 돌리는 명령과 스위트 요약표를 정리해 넣었다.

## 7. 현재 게임 상태 (M5 완료 시점)

```
이동 → 적 스폰 → 자동 조준 사격 → 처치 → 경험치 젬 드랍
    → 자석 수집 → 레벨업 → 화면 정지 → 3택 선택 → 재개
```

한 판의 뼈대가 전부 이어졌다. 다만 **선택한 업그레이드가 아직 아무 효과도 없다**(M6에서 연결). `upgrade_chosen(id)` 시그널을 이미 내보내고 있으므로, M6은 이 시그널을 받아 실제 수치를 바꾸면 된다. UI 스크립트는 건드릴 필요가 없다.
