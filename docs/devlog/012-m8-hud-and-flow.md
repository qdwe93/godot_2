## 2. 시행착오 ① — 틀린 문서가 세 마일스톤 뒤에 청구서를 보냈다

HUD를 만들고 테스트를 돌렸더니 타이머만 0에서 멈춰 있었다.

```
TEST_CASE timer_runs_and_formats FAIL before=0.0000 after=0.0000 formatted=2:07
TEST_CASE timer_stops_on_death   PASS after_death=0.0000 after_frames=0.0000
```

`_process`가 아예 호출되지 않고 있었다. 원인은 HUD 루트의 `process_mode = 2`였다.

### 값이 뒤바뀐 채 문서에 남아 있었다

M5b에서 레벨업 UI를 만들며 `process_mode` 표를 개발일지에 적었는데, **2와 3을 뒤바꿔 적었다.** M5b는 우연히 정상 동작했다 — 의도는 `WHEN_PAUSED`였고 실제로 넣은 3은 `ALWAYS`였는데, "일시정지 중에 버튼이 눌린다"는 목적은 둘 다 만족하기 때문이다. **틀린 값이 틀린 결과를 내지 않아서 발견되지 않았다.**

그리고 M8a의 작업지시서를 쓰면서 내 문서를 그대로 믿고 "ALWAYS(값 2)"라고 적었다. HUD는 `WHEN_PAUSED`가 되어 **평소에는 멈춰 있고 일시정지 중에만 도는** 노드가 됐다.

엔진에 직접 물어보니 답은 한 줄이었다.

```
INHERIT=0 PAUSABLE=1 WHEN_PAUSED=2 ALWAYS=3 DISABLED=4
```

### 교훈

- **열거형의 숫자 값을 기억으로 쓰지 않는다.** 확인은 `print(Node.PROCESS_MODE_ALWAYS)` 한 줄이면 된다.
- **틀린 문서는 틀린 코드보다 오래 산다.** 코드는 실행하면 틀린 게 드러나지만, 문서는 다음에 그걸 믿고 쓰는 사람이 나올 때까지 조용히 기다린다. devlog 007의 표를 정정하고 왜 틀렸는지까지 남겨뒀다.
- 이 프로젝트에서 **에러 없이 조용히 잘못 도는** 유형이 또 하나 늘었다. 목록: `.tscn`의 `script` 선언 순서, 람다 값 캡처, `--capture-frames`의 프레임/시간 혼동, 그리고 이번 `process_mode`.

## 3. 시행착오 ② — 또 케이스 간 상태 오염

타이머를 고치자 이번엔 "사망 시 타이머 정지" 케이스가 실패했다. 사망 처리를 했는데 타이머가 계속 돌았다.

원인은 **무적 시간**이었다. 앞선 케이스에서 플레이어에게 10 피해를 줬고, 무적 0.5초가 걸려 있었다. 이후 케이스들이 진행된 시간은 0.18초뿐이라, `take_damage(999999)`가 **조용히 무시**됐다. 플레이어는 죽지 않았고, 타이머는 당연히 계속 돌았다.

증상("타이머가 안 멈춘다")과 원인("플레이어가 죽지 않았다")이 완전히 다른 층에 있었다.

```gdscript
_player.call("advance_invincibility", 10.0)   # 남은 무적을 먼저 태운다
_player.call("take_damage", 999999.0)
```

M6b에서도 똑같은 종류를 겪었다(기본 총이 궤도구 피해 측정을 오염시킨 건). **케이스가 앞선 케이스의 상태를 물려받으면 엉뚱한 것을 측정한다.**

덤으로 이 케이스는 원래 `after_death == after_frames`만 봤기 때문에 **0 == 0으로도 통과**했었다. 타이머가 아예 안 돌던 첫 실행에서 PASS가 찍힌 이유다. `after_death > 0` 조건을 추가했다.

## 4. HUD 설계 — 두 가지 사소하지만 중요한 것

### 시그널만 듣는 HUD는 처음에 비어 있다

`health_changed`는 **변할 때만** 발생한다. 연결만 해두면 플레이어가 처음 맞을 때까지 HP 표시가 비어 있거나 0이다. 그래서 `_ready()`에서 현재 값을 한 번 직접 읽어 채운다. 테스트 케이스 1이 이걸 검사한다.

### 킬 카운트는 컨테이너 범위로 좁혀서 연결

킬 수를 세려면 각 적의 `died` 시그널을 받아야 하는데, 적은 계속 새로 생긴다. M5a에서 이런 상황에 `get_tree().node_added` 전역 훅을 썼다가 되돌린 적이 있다(플레이어도 `died`를 갖고 있어서 오작동).

이번엔 **`EnemyContainer`의 `child_entered_tree`**를 썼다. 적은 반드시 이 컨테이너 아래에만 추가되므로(M2의 규약), 이 시그널은 정확히 "새 적이 생겼다"를 뜻한다. 전역 훅보다 싸고, 무관한 노드가 걸릴 일이 없다.

M2에서 컨테이너를 따로 둔 결정이 여기서 또 값을 했다.

## 5. 재시작의 함정 — `paused`는 씬이 아니라 트리의 속성이다

```gdscript
func restart() -> void:
    get_tree().paused = false          # 반드시 먼저
    get_tree().reload_current_scene()
```

게임오버 화면은 `paused = true` 상태다. 여기서 바로 `reload_current_scene()`을 부르면, **새 씬이 멈춘 채로 시작한다.** `paused`는 `SceneTree`의 속성이라 씬을 갈아끼워도 남기 때문이다.

증상은 "다시 시작을 눌렀는데 아무것도 안 움직인다"이고, 에러는 없다. 순서 한 줄 차이다.

테스트는 실제로 `reload_current_scene()`을 부를 수 없다 — 테스트 러너 자신이 사라진다. 그래서 `reload_on_restart` 익스포트를 두고 테스트에서 false로 꺼서, **정지 해제까지의 코드 경로는 실제와 동일하게** 검증한다.

## 6. `--auto-play` — 자동화가 막히는 지점을 한 번에 뚫는다

타이틀 화면을 넣는 순간 문제가 생긴다. **모든 자동화 실행이 타이틀에서 영원히 멈춘다.** 캡처도, 밸런스 측정도, 장시간 실행도 전부.

거기에 M7a에서 이미 알던 문제가 하나 더 있다. 무인 실행은 첫 레벨업에서도 멈춘다(3택 버튼을 누를 사람이 없어서).

두 문제를 플래그 하나로 묶었다.

```powershell
... --path "<프로젝트>" -- "--auto-play" "--capture=<경로>.png" "--capture-after=95"
```

`--auto-play`는 ① 타이틀을 건너뛰고 ② 레벨업 UI가 뜨면 매 프레임 첫 선택지를 자동으로 고른다. 이 처리는 `game_flow.gd` 안에 있으므로 **캡처 도구(`capture_helper.gd`)는 손대지 않았다.** 자동화 관련 관심사가 한 파일에 모였다.

> 게임에 "사람의 입력을 기다리는 지점"을 만들 때마다, **자동화에도 그것을 대신할 경로**를 같이 만들어야 한다. 안 그러면 그 순간부터 자동 검증이 불가능해진다.

## 7. 검증 결과

실제 실행 로그:

```
FLOW_STARTED auto=true
FLOW_GAME_OVER time=1:14 kills=43 level=3
PLAYER_DIED survival_time=74.466
```

화면 캡처 3장으로 확인했다.
- **타이틀**: "탕탕 서바이버" + 부제 + 시작 버튼
- **플레이**: HP 100/100, Lv.1, 0:25, 처치 12 — 좌상단·우상단에 각각 배치
- **게임오버**: 생존 시간 1:14 / 처치 수 43 / 도달 레벨 3 + 다시 시작 버튼

HUD의 최대 HP가 120으로 늘어난 것도 보인다 — 자동 선택이 심장(최대 HP +20)을 골랐다는 뜻이고, M6의 업그레이드가 실제 플레이에서 작동하고 있다는 증거다.
